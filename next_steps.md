But it still did not beat the historical best exact-CLI snapshot for `satsolver.py` (`27.1974s`). So future exact-submission work should use `satsolver_fast.py` as the current alternate baseline, and any attempt to merge that win back into `satsolver.py` should target a smarter root-pure policy rather than just deleting the presolve blindly.
21. Do not remove the post-solve `model_satisfies(...)` self-check from `satsolver_fast.py` unless a future benchmark corpus makes that path materially larger. On the current benchmark set, the entire SAT-only check totals just `0.005311s` across all `28` SAT formulas, with the worst single case only `0.000713s`. A repeat-aware exact-CLI rerun of the no-self-check variant still landed at `27.6785s`, worse than the retained `satsolver_fast.py` snapshot `27.3829s`. So CLI-only safety removals of this size are not worth keeping.
22. Do not assume parser-integrated first-round-pure gating is enough to rescue root-pure preprocessing on `satsolver_fast.py`. Even after confirming that all current root-pure hit cases already have `first_round_pure_count >= 2`, a branch that collected those counts during DIMACS parsing and only then ran iterative root-pure preprocessing was still a near-tie at best: it regressed slightly on the exact-CLI root-hit slice (`0.4382s -> 0.4407s`) and was only effectively tied on the mixed exact-CLI slice (`24.6599s -> 24.6480s`). So future exact-CLI root-pure work still needs a materially stronger classifier or a broader win than this parser-gate branch showed.
23. Do not assume a standalone no-root-pure copy of the full solver is better than the current wrapper-style `satsolver_fast.py`. A branch that replaced the wrapper with a copied `satsolver.py` minus root-pure presolve regressed badly on the exact-CLI root-hit SAT slice (`0.4336s -> 0.4996s`) and was only slightly positive on the mixed nine-case hotspot slice (`24.4869s -> 24.4441s`). So future alternate exact-CLI files need to be materially smaller or more structurally different than a duplicated main solver, not just “the same code without root-pure.”
24. Do not assume a smaller wrapper around the same no-root-pure alternate core is enough to beat the retained `satsolver_fast.py`. A scratch min-wrapper that trimmed the current alternate file down further still lost the exact-CLI root-hit SAT slice on the two-order average (`0.4159s -> 0.4511s`) and then lost the repeat-aware exact-CLI 59-case suite overall (`27.3829s -> 27.5180s`), even though it improved the mixed nine-case hotspot slice (`24.8028s -> 24.5644s`). So future alternate exact-CLI file work needs a more meaningful semantic or code-size win than wrapper reshaping around the same no-root-pure solver core. The same cycle also measured full-corpus structural presolver cost directly: pigeonhole plus XOR checks totaled only about `0.0643s` across all 59 benchmark cases, so dropping those presolvers is unlikely to be the next useful exact-CLI lever either.
25. Do not assume a lazy-import alternate file with duplicated parser/output/structural presolvers is enough to beat the retained `satsolver_fast.py`. A scratch `scratch_satsolver_fast_lazy.py` did improve the six-case structural-hit exact-CLI slice (`0.1811s -> 0.1780s`), stayed slightly positive on the mixed nine-case hotspot slice (`24.7933s -> 24.7768s`), and even beat the retained alternate on a same-day exact-CLI single-run full suite (`27.1851s -> 26.9872s`). But it still lost the repeat-aware exact-CLI 59-case gate at `27.5546s`, worse than the retained `27.3829s`. So future alternate exact-CLI file work should not trust startup-sensitive slice wins or a one-off full-suite win by themselves; it still needs a stronger repeat-aware suite-level signal than “lazy-load the main solver behind duplicated structural presolvers.”
26. Do not drop the structural pigeonhole/XOR presolvers from future exact-CLI alternate files just because their aggregate corpus cost is small. A scratch lazy-core alternate that kept only local parse/output work and lazy-imported the solver core without those presolvers regressed the SAT-heavy root-hit slice (`0.4081s -> 0.4182s`) and catastrophically regressed the mixed exact-CLI hotspot slice (`24.3616s -> 32.2099s`) because `special/tseitin.cnf` alone blew up from about `0.03s` to about `7.43..7.46s`. So future alternate-file work should treat those structural shortcuts as required exact-CLI fast exits, not optional startup overhead.
27. Treat exact-CLI DIMACS parse/write overhead as a real but small lever on `satsolver_fast.py`. Replacing the inherited text parser/writer with a byte-level local `parse_dimacs[_file]()` plus byte-output path improved the same-day SAT-heavy root-hit exact-CLI slice (`0.4431s -> 0.4319s`) and improved the same-day repeat-aware exact-CLI 59-case comparison against the retained wrapper from `27.6459s` to `27.4523s`, both `59/59` correct. But the mixed nine-case hotspot slice was effectively tied (`24.6944s -> 24.6945s`), the refreshed merged artifact still landed at `27.5074s`, and the historical best retained `satsolver_fast.py` snapshot `27.3829s` remains unbeaten. So future alternate exact-CLI file work can revisit parser/read/write overhead, but it should treat gains here as sub-1% and noisy, require same-day repeat-aware baseline-vs-candidate measurements, and still keep the structural pigeonhole/XOR presolvers intact.
28. Do not assume the same byte-level DIMACS parse/write path that helped `satsolver_fast.py` will also help the main submission file `satsolver.py`. A main-solver branch using byte-level `parse_dimacs_file()` and byte-output `write_result()` improved the exact-CLI SAT-heavy root-hit slice (`0.4960s -> 0.4718s`) and was nearly tied on the mixed nine-case hotspot slice (`24.6647s -> 24.6994s`), but it still regressed the same-day repeat-aware exact-CLI 59-case suite badly (`27.6153s -> 29.3807s`), both `59/59` correct. So future parser/read/write work should stay on alternate exact-CLI wrappers unless a main-solver branch can clear the same-day repeat-aware full-suite gate; slice-local wins are not enough.
29. Treat lazy structural wrappers around `satsolver_fast.py` as another dead end unless the future design is materially different. A second-generation scratch wrapper with local byte-level parse/output, local structural pigeonhole/XOR fast exits, and lazy import of `satsolver_fast` still regressed the structural-hit slice (`0.1857s -> 0.1924s`), the SAT-heavy root-hit slice (`0.4189s -> 0.4208s`), and the mixed nine-case hotspot slice (`24.3005s -> 24.6247s`). So the “do local structural checks, then import the current alternate solver anyway” idea does not appear to recover the old lazy-import story after the bytes-parser keep.
30. Treat direct streamed-file DIMACS parsing in `satsolver_fast.py` as another dead end unless a future parser design removes materially more work than the current byte parser does. A scratch candidate that replaced the retained `read() + splitlines()` byte parser with a streaming binary-line loop regressed the first exact-CLI gate from `0.3701s` to `0.3931s` on the SAT-heavy root-hit slice (`0.3721s -> 0.3778s` forward, `0.3680s -> 0.4083s` reverse). So parse-path work on the alternate exact-CLI file now looks especially noise-sensitive and should demand a stronger same-day signal before earning broader benchmarking.
31. Treat “replace the narrow portfolio gate with one serial phase-biased worker” as another dead end. A branch that changed `satsolver_fast.py` so the current portfolio gate called `solve_cnf_serial(..., seed_phase_bias=True)` instead of the two-worker portfolio did produce a real exact-CLI `large/test_8.cnf` win (`0.2922s -> 0.2207s` two-order average), but it still lost the mixed nine-case exact-CLI hotspot slice overall (`24.3702s -> 24.5513s`) because the reverse-order regressions outweighed the forward win. So future portfolio work still needs a broader suite-level story than just avoiding `fork()` on the one gated SAT-like family.
32. Treat broader learnt-database trimming aggressiveness as another dead end unless a future idea brings a materially better classifier than “same ranking, keep a smaller fraction.” A branch that changed `reduce_database()` to keep only the top `40%` of ranked candidates instead of the top `50%` blew up the mixed nine-case exact-CLI hotspot slice from `24.6309s` to `40.4076s`, with `large/test_8.cnf` alone jumping from about `0.29s` to about `12.18s`. So future learnt-large watcher work should not try to solve the problem by simply trimming the ranked candidate pool harder across the board.
33. Treat parser-path work in `satsolver_fast.py` as another exhausted lane unless the future design changes much more than how the bytes are tokenized. A scratch manual byte-scanner parser regressed the first exact-CLI gate from `0.4605s` to `0.4908s` on the SAT-heavy root-hit slice, after the earlier streamed-line parser already lost `0.3701s -> 0.3931s`. So the retained bytes parser keep now looks like the end of the easy exact-CLI parser wins, not the start of a larger parser-optimization ladder.
34. Treat “same ranking, same keep fraction, reduce sooner” as another learnt-database dead end unless a future branch brings a materially better classifier than a smaller `next_reduce` multiplier. A branch that only changed the post-reduction schedule from `int(len(self.learnt_ids) * 1.5) + 64` to `int(len(self.learnt_ids) * 1.25) + 64` regressed the mixed nine-case exact-CLI hotspot slice from `24.4791s` to `30.9079s`, with `large/test_8.cnf` alone jumping from about `0.29s` to about `2.32s` and the dense UNSAT cases also getting worse. So future learnt-large work should not assume that “reduce earlier” is a safer version of aggressive trimming.
